# Alarm Calendar: MVP Spec

Build instructions for Claude Code. Read the whole file before writing code. Build in the order given in section 12 and stop to verify at each checkpoint.

## 1. What this is

A minimal personal calendar where every event fires a loud, full-screen alarm on PC and Android, not a notification. The alarm cannot be silently swiped away. You either mark it Done or snooze it, and snoozes are limited per event. A weekly cheat pass system lets you skip a whole day without breaking the habit loop.

Single user, no sharing. Speed matters more than polish, but the UI must look clean and modern.

## 2. Stack (decided, don't re-debate)

- **Shared UI:** one React + TypeScript app built with Vite. Tailwind + **shadcn/ui** components + **lucide-react** icons. Dark mode default. Initialize shadcn with the **`b0` preset** (classic black and white defaults): `pnpm dlx shadcn@latest init --preset b0`. Check the current CLI syntax in the docs before running it, and don't restyle the preset's tokens.
- **Docs first, memory never:** before using any API from shadcn/ui, FullCalendar, Capacitor, Electron, Supabase, Tailwind or date-fns, look it up through the **Context7 MCP** (`resolve-library-id`, then `query-docs`) and web search where needed. Versions move fast, so do not write from memory. This applies especially to the shadcn CLI, the Supabase key format, and Capacitor plugin APIs.
- **UI/UX skill:** the UI/UX skill installed in Claude Code must be invoked before designing or building any screen (calendar, event sheet, settings, alarm screens, auth). Follow it for layout, spacing, hierarchy and states (empty, loading, error).
- **Calendar views:** **FullCalendar** (`@fullcalendar/react`, `daygrid`, `timegrid`, `interaction`). Theme it with the shadcn CSS variables so it matches. Event occurrences are generated by our own recurrence function (section 5), fed to FullCalendar as plain events. Do not use FullCalendar's rrule plugin.
- **PC:** Electron wrapping the shared React app. Tray app, starts on boot.
- **Android:** Capacitor wrapping the same React app, plus a **custom native Kotlin Capacitor plugin** (`AlarmEngine`) that owns scheduling, the alarm sound, and the alarm screen. The alarm screen itself is a native Kotlin Activity, not the WebView. Reason: reliable alarms need AlarmManager, a foreground service and a full-screen intent, which WebViews can't do.
- **Backend:** Supabase (Postgres, Auth, Realtime, RLS). No custom server.
- **Libraries:** `date-fns` + `date-fns-tz` for time math, `zod` for validation, `@supabase/supabase-js`, `zustand` for client state, `vitest` for tests.
- **Monorepo:** pnpm workspace.

```
/
  packages/core/        pure TS: types, recurrence, snooze logic, cheat pass logic, tests
  app/                  Vite React app (shared UI), imports core
  electron/             main process, tray, scheduler, alarm window
  android/              Capacitor android project + AlarmEngine plugin (Kotlin)
  supabase/migrations/  SQL
```

The UI talks to the platform through one interface, implemented twice (`ElectronAlarmAdapter`, `CapacitorAlarmAdapter`):

```ts
interface AlarmAdapter {
  setSchedule(payload: SchedulePayload): Promise<void>   // the precomputed schedule, see below
  drainCompletions(): Promise<CompletionRow[]>   // completions made while the app was closed or offline
  getPermissionStatus(): Promise<PermissionStatus>
  openPermissionSettings(): Promise<void>
}

interface SchedulePayload {
  version: 2
  generatedAt: string       // ISO UTC, when the list was computed
  horizonEnd: string        // the list is complete for every active event up to here, inclusive
  truncated: boolean        // a size cap shortened the horizon
  settings: AlarmSettings   // timezone, grace_minutes, refire_seconds, ... plus the device's sound id
  occurrences: ScheduleOccurrence[]   // ascending by `at`, then event id
  eventInfo: Record<string, ScheduleEventInfo>   // per active event, even one with no occurrence in the window
  refillSource: { events: EventRow[]; cheatDays: string[] }   // Electron main only; other engines ignore it
}

interface ScheduleOccurrence {   // thin on purpose: what differs per ring
  id: string                // `${eventId}@${at}`, the id the alarm screen and the completion upsert use
  eventId: string
  at: string                // ISO UTC with milliseconds
  silenced: boolean         // a cheat day covers it (passable only): never rings
  completed: boolean        // a completion is known for it, on any device: never rings
  label?: string            // text instead of the event title (a pre-prayer alarm), decided when the list was built
  labelIfUnlogged?: { id: string; label: string }   // shown instead of `label` when occurrence `id` is not completed as this rings
}

interface ScheduleEventInfo {   // what is the same for every ring of an event, stored once
  title: string; notes: string | null
  maxSnoozes: number; snoozeMinutes: number
  soundId: string | null    // a bundled sound id, or 'custom' for the user's own prayer sound file
  kind?: 'prayer' | 'pre_prayer'; prayer?: string   // absent for a normal alarm
}
```

**Precomputed schedule (roadmap v2, phase 3a).** The engines do not compute recurrence. `expandSchedule` and
`buildSchedulePayload` in `packages/core/src/schedule.ts` turn events, cheat days, settings and completions into the
list above: every occurrence from `now` to `now + 60 days`, plus, per event, the latest occurrence inside the grace
window before `now` (at most 7 days back; of several missed ones only the latest can ring), deduplicated, sorted, with
cheat days (by local date in the settings time zone) and completions already applied. A platform engine rings what is in
the list, applies the grace window, the snooze and re-fire rules (sections 6, 9, 10) and tracks its own ringing state,
and needs no recurrence, cheat day, mode or prayer logic. Later phases add their occurrences (prayer times, exam
revision sessions) as further sources of the same record, and modes as transforms of it, inside core.

**Prayer alarms (phase 3b).** `eventOccurrencesBetween` (`packages/core/src/occurrences.ts`) is the one place that
turns an event into instants: a normal alarm follows the recurrence rule, a `prayer` / `pre_prayer` event follows the
prayer times in the settings (and nothing for either while `prayers_enabled` is off, which also leaves them out of
`eventInfo`, so an engine dismisses a ringing prayer). The schedule, the calendar and habit scoring all call it. Prayer
events are never passable (a cheat day does not silence them) and take their snooze rules from settings
(`prayer_max_snoozes`, `prayer_snooze_minutes`), not from the row. The prayer uses the device's prayer sound
(`settings.prayerSound`, a bundled id or `'custom'`), falling back to `settings.sound`; its reminder uses `sound`.
An engine that gets `labelIfUnlogged` on an occurrence shows that text when the occurrence it names is not completed
at ring time (completed flags in the list, completions it knows, or its own pending ones), else `label`, else the title.
For a prayer or pre-prayer event, a completion matches an occurrence by event and prayer-day (`prayerDayKey` in core), not by
exact instant, so editing an offset or the location after "prayed" does not ring or score the moved alarm again; normal alarms
keep matching by exact instant.

Bounds: at most 1500 occurrences per event and 5000 in all. When a cap cuts occurrences off, `horizonEnd` moves back to
just before the first one cut and `truncated` is true, so an engine never reads silence as "nothing scheduled". A cap
never cuts at or before `now` (`horizonEnd` is never earlier than `generatedAt`). `grace_minutes` is validated up to the
7 day look-back, and `buildSchedulePayload` states a larger setting as the look-back.
The app pushes a fresh list on every change, on launch, when the window gains focus, and once a day. An engine that can
re-expand itself (Electron main, via `refillSource`) does so when under 7 days of horizon remain and at least daily.
`eventInfo` is how an engine learns an event was deleted or switched off: it dismisses a ringing or snoozed
alarm only when its event has no entry there (an occurrence that has aged out of the list, such as a snooze longer than the
grace window, must not end the alarm). An older renderer that still pushes the version 1 payload (`events`, `cheatDays`,
`settings`, `completions`) is accepted by Electron main, which expands it with the same core function.

All tables have RLS: `user_id = auth.uid()` for select/insert/update/delete.

Unique `(event_id, occurrence_at)`. Writes are upserts so offline flushes are idempotent.

**settings** (one row per user): `timezone` (IANA, default from device), `week_starts_on` (0 = Monday default), `refire_seconds` (default 120), `pass_cap` (default 2), `grace_minutes` (default 30).

Prayer columns (roadmap-v2 phase 3b), all with defaults for Ariana, Tunis: `prayers_enabled` (false), `prayers_enabled_since`, `latitude` (36.8625, range -65 to 65) / `longitude` (10.1956), `location_label`, `fajr_angle` / `isha_angle` (18, range 10 to 22), `asr_factor` (1 or 2), `fajr_offset_min` ... `isha_offset_min` (-60 to 60), `pre_prayer_minutes` (15, 0 to 120, 0 = no reminders), `prayer_max_snoozes` (0, 0 to 10), `prayer_snooze_minutes` (5, 1 to 120). The RPC `set_prayers_enabled(boolean)` switches them on (creating or re-activating the 10 rows) or off (deactivating them) in one transaction.

**pass_wallet** (one row per user): `balance` int, `last_granted_week_start` date.

**cheat_days**: `id`, `user_id`, `day` date (in the user's timezone), `created_at`. Unique `(user_id, day)`.

## 5. Recurrence (packages/core)

One pure function, implemented in TS and mirrored in Kotlin, with shared test vectors (JSON file both test suites read):

```ts
nextOccurrence(event, afterInstant, tz): Date | null
occurrencesBetween(event, from, to, tz): Date[]
```

Rules:
- `hour`: absolute interval math from `start_at` (every 12 hours is exactly 12 real hours).
- `day`, `week`, `month`, `year`: **wall-clock time in the user's timezone**, so 08:00 stays 08:00 across DST changes.
- `week` with `repeat_weekdays`: occurrences on those weekdays in every Nth week, counting weeks from the week of `start_at`.
- `month`: same day of month as the start. If the month is shorter, clamp to the last day (31st becomes 30th or 28th). Don't skip the month.
- `year`: same month and day as the start, every N years. A 29 February start falls on 28 February in common years and on the 29th again in leap years (clamped from the original date each year, no drift).
- Respect `ends_at` and `active`.
- Never produce an occurrence before `start_at`.

Tests must cover: every 12 hours across a DST change, every 3 days, monthly on the 31st, biweekly on Mon and Thu, and an event ending mid-series.

## 6. Alarm behavior (both platforms)

Per occurrence, state: `pending -> ringing -> (snoozed -> ringing)* -> done`.

1. At `occurrence_at`, unless it falls on a cheat day and the event is `passable`, start ringing.
2. Ringing means: sound looping at full alarm volume, full-screen UI with the event title, the time, and big buttons.
3. **Done** writes a completion (`status = done`, `snoozes_used`), stops the sound, schedules the next occurrence.
4. **Snooze** is shown only if `snoozes_used < max_snoozes`. The label shows what is left: "Snooze 5 min (2 left)". Pressing it stops the sound and re-rings after `snooze_minutes`, `snoozes_used += 1`. At the limit the button disappears and the screen shows "No snoozes left, do it now". With `max_snoozes = 0` the button never appears.
5. **No other way out.** If the window or activity is closed, killed, or swiped away without Done or Snooze, it re-rings after `refire_seconds` (default 120) and keeps doing so.
6. Missed alarms: if the device was off or asleep and comes back within `grace_minutes` of an uncompleted occurrence, ring immediately. Older than that, ignore (no completion row needed in v1).
7. If another occurrence of the same event comes due while one is still ringing, drop the new one.
8. Alarms are scheduled **locally from cached data** and must work with no internet. Local state of snoozes and pending completions lives on the device until it syncs.
9. Each device handles its own ringing independently in v1. Done on one device does not silence the other. Both write the same upsert, which is fine.

## 7. Cheat pass system

A currency that lets you skip a whole day without burnout.

**Rules**
- One pass is granted at the start of each week (week start comes from settings, default Monday).
- Balance cap is **2**. If you are already at 2, the weekly grant is lost.
- New accounts start with 1 pass.
- Spending a pass picks a day: today or any future day. That day becomes a cheat day. Max one cheat day per calendar day.
- On a cheat day, every event with `passable = true` is silenced (no alarm). Events with `passable = false` ring normally (medication, etc.).
- Undoing a cheat day before it starts (it's still in the future, not today) refunds the pass. Today's cheat day can't be undone once the day has begun.

Example of the cap behavior:

| Week | Start balance | Grant | Used | End balance |
|---|---|---|---|---|
| 1 | 1 | (initial) | no | 1 |
| 2 | 2 | +1 | no | 2 |
| 3 | 2 | +1 capped | yes | 1 |
| 4 | 2 | +1 | yes | 1 |

**Implementation**
- Postgres RPC `sync_wallet()`: computes the current week start in the user's timezone, then for every week boundary since `last_granted_week_start` does `balance = min(balance + 1, pass_cap)`, then updates `last_granted_week_start`. Call it on app launch and on focus. Catch-up must handle being away for several weeks.
- Postgres RPC `use_pass(day date)`: single transaction. Fails if balance is 0, if the day is in the past, or if the day is already a cheat day. Decrements balance, inserts into `cheat_days`.
- Postgres RPC `refund_pass(day date)`: only for future days, deletes the cheat day and increments balance (respecting the cap).
- Using or refunding a pass requires internet in v1. After success the app pushes the updated `cheat_days` list to the AlarmAdapter so devices silence alarms locally.
- Calendar shows cheat days with a subtle striped background and a badge. Silenced occurrences on that day render greyed out.

**UI**
- Header chip: ticket icon plus "Pass 1/2".
- Button opens a dialog: pick a day (shadcn Calendar), confirm, "This silences N events on that day."
- A small line under the chip: "Next pass: Monday" (or "At cap" when at 2).

## 8. UI

**Component consistency is a hard rule.** Every interactive or form element comes from shadcn/ui, installed via the CLI (`shadcn add ...`). Before building any UI piece, check the shadcn docs (through Context7 and the web) for an existing component, and use it. Native HTML controls are banned for anything the user sees:
- No `<input type="checkbox">`, `<input type="radio">`, `<select>`, `<input type="date">` or `<input type="time">`, `<button>`, or `<dialog>`. Use Checkbox, Radio Group, Select, Calendar + Popover (date), a shadcn-style time input, Button, Dialog.
- Expected components: Button, Input, Textarea, Label, Checkbox, Switch, Select, Radio Group, Toggle Group, Slider or number stepper built from Button + Input, Calendar, Popover, Dialog, Sheet, Drawer (mobile bottom sheet), Tabs, Badge, Card, Separator, Tooltip, Sonner (toasts), Form (react-hook-form + zod), Input OTP (for the sign-in code), Alert, Skeleton, Scroll Area.
- Icons are lucide-react only, no emoji and no other icon sets.
- If shadcn truly has no component for something, say so in a code comment and compose it from shadcn primitives with the same tokens. Do not introduce a second UI library.
- **FullCalendar is the one exception** (it renders its own markup). Theme it with the shadcn CSS variables (`--background`, `--border`, `--primary`, `--muted`, etc.) so it blends in, and render its toolbar buttons with shadcn Buttons instead of its default ones.
- The native Android alarm screen can't use shadcn. Mirror the same look there: black and white, same radius, same type scale, large rounded buttons.

Dark by default with a light toggle.

Screens:

## 9. Electron specifics

- Main process owns the scheduler, not the renderer, so alarms fire even if the main window is closed. Closing the main window hides to tray. Quit only from the tray menu.
- Autostart: `app.setLoginItemSettings({ openAtLogin: true })`. Add a toggle in Settings.
- Scheduler: works from the precomputed occurrence list (section 2) held in the cache: one `setTimeout` to the soonest occurrence not yet handled, plus the wake-up times of snoozed and re-firing alarms. Also re-evaluate every 30 seconds and on `powerMonitor` `resume` and `unlock-screen`, to survive sleep and timer drift. Apply the grace-window rule on resume.
- Alarm window: `BrowserWindow` with `frame: false`, `alwaysOnTop: true` at level `screen-saver`, `skipTaskbar: false`, `fullscreen` or maximized, focused, no close button. Loads the React route `/alarm?occurrence=...`. If it gets closed anyway, the main process re-opens it after `refire_seconds`.
- Sound: HTMLAudioElement looping in the alarm window, bundled mp3.
- Local cache: the occurrence list, the events, cheat days and settings it was built from (main re-expands the list from them, see section 2), the ringing and snoozed state, and pending completions in a JSON file in `userData` (`version: 2`; a version 1 file is migrated on load and its list rebuilt on the first start). Sync from Supabase on launch plus a realtime subscription, flush pending completions when online.
- Known limit: always-on-top does not draw over **exclusive fullscreen** games. Document this in the README: run matches in borderless windowed. Sound and taskbar flash still happen.

## 10. Android specifics (AlarmEngine plugin, Kotlin)

Components:
- **Plugin class** exposing the `AlarmAdapter` methods. `setSchedule` stores the precomputed `SchedulePayload` (section 2) in local storage (Room or SharedPreferences JSON) and reschedules. Nothing in it needs the recurrence mirror.
- **Scheduler:** from the stored occurrence list take the soonest one that is not `silenced`, not `completed` and not yet handled, and schedule it with `AlarmManager.setAlarmClock()` (Doze exempt, shows the system alarm icon). When one fires, schedule the next soonest. Snoozes and re-fires use `setAlarmClock` too.
- **AlarmReceiver** (BroadcastReceiver) starts **AlarmService**.
- **AlarmService:** foreground service, notification channel with importance HIGH and a **full-screen intent** pointing to AlarmActivity. Plays the sound looping on `AudioAttributes.USAGE_ALARM` at the alarm stream volume, holds a partial wake lock while ringing.
- **AlarmActivity:** native screen, `setShowWhenLocked(true)`, `setTurnScreenOn(true)`, keeps the screen on. Shows title, time, Done, and Snooze (with remaining count, hidden when none left). Style it dark and clean to match the app: big type, large rounded buttons. Back button is disabled. If it is dismissed without a choice, AlarmService schedules a re-fire after `refire_seconds`.
- **BootReceiver:** `BOOT_COMPLETED` and `MY_PACKAGE_REPLACED` reschedule from local storage. Also reschedule on time or timezone change broadcasts.
- **Offline completions:** Done writes to a local queue. The plugin's `drainCompletions()` returns and clears it, and the JS side upserts to Supabase.
- **Permissions and manifest:** `SCHEDULE_EXACT_ALARM` (and `USE_EXACT_ALARM` if it fits the target policy), `USE_FULL_SCREEN_INTENT`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE` plus the proper foreground service type, `WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED`, `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.
- **Permission flow:** on first launch and on every launch after, `getPermissionStatus()` checks exact alarm, full-screen intent (revocable on Android 14+), notifications, and battery optimization. If anything is missing, show a blocking shadcn Dialog explaining why with a button that deep-links to the right settings screen via `openPermissionSettings()`.

Target a recent `targetSdk`. Test on a real device, not only the emulator.

## 11. Out of scope for v1

iOS, Google sign-in, magic-link redirects, Google Calendar import, categories or tags beyond color, shared calendars, cross-device dismiss, widgets, streak statistics, "Nth weekday of the month" rules, editing a single occurrence of a series, spending passes offline, push notifications.

## 12. Build order (stop at each checkpoint)

1. **Monorepo and core.** Types, `occurrencesBetween` / `nextOccurrence`, snooze and wallet logic as pure functions, full test suite including the shared JSON vectors. Checkpoint: tests green.
2. **Supabase.** Migrations, RLS, enums, `sync_wallet`, `use_pass`, `refund_pass`. Checkpoint: call the RPCs from a script and verify the table in section 7.
3. **Android alarm engine with hardcoded events.** Scheduler, service, activity, boot receiver, snooze limit. This is the riskiest part, prove it first. Checkpoint: alarm fires with the screen off and the app swiped away, snooze limit works, re-fire works after a swipe, survives reboot.
4. **Electron alarm engine with hardcoded events.** Scheduler, alarm window, tray, autostart, resume handling. Checkpoint: same behaviors as above on PC.
5. **React app:** auth, event form, Week / Month / Agenda views, settings, pass chip and dialog. Run in the browser first against Supabase.
6. **Wire the adapters** (`setSchedule`, `drainCompletions`, permissions) on both platforms, replace the hardcoded events with synced ones, add realtime subscription and local cache.
7. **Polish and README:** permission flow copy, exclusive-fullscreen note, build commands for the Electron installer and the Android APK.
